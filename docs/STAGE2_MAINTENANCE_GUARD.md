# Optional maintenance-outage exclusion

The frozen strong-mode cohort has four INVALID turbo n24/seed4 traces, not432 valid traces. Independent reproduction identifies MAINTENANCE reservations on F2 during its revealed720–1080 outage: starts722,720,780,960 for WIP6/8 ×QA guard0/4. Production `process()` already rejects the observed outage, but `service_resources()` has a separate maintenance loop that omits that test. The checker correctly rejects these physical overlaps. Turbo reaches the wear threshold during the outage; this is not a hidden setup crossing or a quantum decode issue.

`stage2/maintenance_guard.py` supplies `MaintenanceOutageGuardMixin` and named recovery/scoped-routing classes. The explicit constructor flag is `maintenance_outage_guard=False` by default. Convenience `run(instance,weights=None,controller=None,*,admission=False,maintenance_outage_guard=False,**recovery_routing_options)` preserves the original behavior when off. `AdmissionMaintenanceGuardFactory` is the corresponding family-admission class. No physical core, checker, shared dispatcher, mode or outcome is edited.

When enabled, the guard considers a currently maintenance-eligible machine's actual maintenance duration. It suppresses that start if its half-open interval overlaps either a currently revealed outage event or any outage in the still-unrevealed public scenario support. It never reads which future outcome will occur. Finishing exactly at outage start is allowed; starting at outage end is allowed. Conservative support exclusions can delay maintenance even on a tape that later reveals no outage, so equality is only guaranteed when no relevant observed/public-support restriction binds.

Suppression is scoped only to `service_resources()`: the machine busy cache is temporarily marked unavailable, then restored in `finally`, including failures during guard selection or the parent service call. The full machine dictionary stays present so portable-tool service hall lookup remains correct. Worker and tool dictionaries are not filtered or rolled back; legitimate unrelated service bookings remain committed. Unexpected changes to a blocked machine booking raise an explicit error after restoring all temporarily altered caches. No maintenance duration, power, workforce, wear or physical outage is relaxed.

Seven tests cover exact default physical equivalence; half-open boundary/public-support causality; service and selection exception restoration; machine/hall/worker/tool cache integrity; preservation of legitimate other service bookings; no-outage-support equality and actual paired causality; and all four original invalid cases versus checked guarded executions. The final-source diagnostic retains all eight full traces under `output/stage2-search/maintenance-outage-diagnostic-final/`: four unguarded traces remain INVALID and four guarded traces pass the independent checker. The earlier source/prototype evidence remains separately retained in `maintenance-outage-diagnostic/`. This is a targeted correctness repair, not an unbiased performance comparison or a claim that every other policy is valid.

Static factory compositions may explicitly select this guard. Frozen MPC/adaptive continuations must not silently gain it: any such composition requires a separate runner/source audit and consistent actual/future factory classes. Inheriting the mixin before scenario deepcopy is technically possible but has not been selected or claimed as validated here. Existing historical results remain labeled with their original guard setting and validity.
