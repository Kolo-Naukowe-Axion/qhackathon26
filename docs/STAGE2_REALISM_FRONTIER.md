# Measured price of realism in the full-recipe model

17 October 2026. This completed local experiment removes one modeled feature at
a time from the same32-operation replacement-heat-capacity fixture. All feature
cases retain the same operations, machines, workers, horizon1440 and grid30.
These are **different factory models**, not lossless transformations of the full
model. Within each case, complete unary and exact support pruning retain its
feasible schedules; a cap24 operation pool is deliberately lossy.

The [source-sealed experiment](../output/realism-frontier-v1/report.json) contains
six feature cases plus32/64/128-operation scaling. Each parent is generated by
the same seeded list heuristic before native references, with no optimum given
to candidate generation. Native CP receives raw model data, and pool CP receives
raw columns rather than QUBO coefficients. Every returned plan is independently
checked. Compilation counts, coefficient ranges, hashes and build timings are
saved; the complete ablation campaign takes112.57seconds on this machine.

## Completed fixed-horizon feature accounting

Counts below include the compiler's makespan register. The naive assignment
product is34,300 in all six cases: eligible machines × every worker × every
grid start, before skills/calendars/releases/durations. This is an exact
variable-family count, **not a compiled naive QUBO**. Its18,950,750 one-hot
couplers are only a lower bound; no full naive coefficient matrix is claimed.

Every complete and restricted reference in this feature table is certified
OPTIMAL in its own model/domain. The last row sets terminal due dates to the
original horizon, so its zero tardiness is defined against those changed dates;
it does not show an on-time plan under the original minute900 deadlines.

The first campaign intentionally guarded the continuous-calendar complete
build:14,688 unary assignments require104,349,594 cross-operation checks. That
guard is preserved in its output. The table fills those coefficient counts
using a separate [exact blockwise audit](../output/realism-continuous-counts-v2/report.json),
which takes2.80seconds without allocating a global quadratic dictionary. Its
largest Boolean operation-pair block has324,900 cells. Vectorized support
propagation retains9,180 assignment rows plus142 makespan bits. The scalar
conflict implementation and literal tiny compiler independently check the
blockwise reason multiplicities, coefficient extrema, support results and
coupler counts in tests. It is a count/representation audit, not a solver run.
The preliminary `realism-continuous-counts-v1` has a corrected setup-multiplicity
bug and is retained only as failed development evidence; use v2.

There are useful measured nonmonotonic effects:

- Worker calendars make the physical schedule slower here, but shrink its
  support-pruned encoding from9,322 to2,499 bits. This is exact preprocessing,
  not evidence of improved QAOA or VeloxQ success.
- Removing transfer lags decreases direct incompatibilities, but weakens
  support pruning enough to **increase** the final graph to457,015 couplers.
- Machine setups add6,890 couplers without adding support-pruned bits, while
  leaving the optimum unchanged in this case. Retain that negative result.
- Removing deadline costs leaves the support graph unchanged but reduces its
  largest signed coefficient from4,543,428 to4,278 under this compiler's original
  bound. A feature can affect coefficient scale without adding variables.

All coefficient ranges and build times appear per representation in the JSON
reports. They use original compiler penalties; the previously saved recovery
packets may use incumbent-tightened penalties. Those landscapes must not be
silently interchanged in a solver comparison. The unary complete compiler also
uses a different completion-register convention from the operation-column
compiler, so raw total-bit differences are not purely candidate-domain savings.

## Scaling with honest bounds

Scaling uses the saved nominal recipes, with horizons1440/2880/4320 respectively
and grid30. Unlike the feature table, these horizons intentionally vary. The
native solve cap is10seconds with one worker; construction time is additional.

Bounds are for each nominal original objective. The upper endpoints are
independently checked heuristic or pool witnesses; the lower endpoints are
native CP bounds. UNKNOWN does not mean infeasible, and a restricted optimum
does not certify a global optimum. Full explicit compilation at64/128 is
skipped by the predeclared variable/pair guard. These are disclosed limits of
this implementation, not evidence that other complete formulations cannot fit.
